## Constats et corrections, par priorité

### P0 — garde-fous aveugles et sécurité

**1. Le lint frontend ne lit qu'un quart du code.**
`expo lint` sans argument ne lint que `src/`, `app/` et `components/`. KeepEat range son code dans `app/`, `component/` (singulier), `store/`, `utils/`, `data/`. Résultat : 31 erreurs invisibles, dont 14 `console.log` dans `store/authStore.ts` qui court-circuitent le logger central et journalisent l'adresse e-mail à la connexion (`login called with email:`). La règle `no-console: error` existe dans `eslint.config.js`, elle n'est simplement jamais appliquée là où ça compte.
→ `"lint": "eslint ."` avec `ignores` pour `.test-dist`, `.expo`, `dist`, `android` ; corriger les 31 erreurs (logger + retrait de l'e-mail des logs) ; les 50 avertissements en suivant.

**2. Dépendances backend vulnérables et non maintenues.**
`pymongo==4.5.0` (2023) cumule 7 avis de sécurité ; `python-jose` est abandonné (et tire `ecdsa`, lui aussi signalé) ; `passlib` est abandonné et force `bcrypt==4.1.3`. Le reste est en `>=` non épinglé, donc chaque déploiement Render peut installer autre chose que ce qui a été testé.
→ `pymongo`/`motor` à jour ; `python-jose` → `PyJWT` (même API, 3 lignes dans `auth_utils.py`) ; `passlib` → `bcrypt` direct ; versions épinglées ; `pip-audit` dans la CI.

**3. Connexion biométrique : le mot de passe est stocké en clair.**
`utils/biometricAuth.ts` sérialise `{email, password}` dans SecureStore, puis rejoue un login classique. SecureStore chiffre et exige l'empreinte à la lecture, mais c'est le mot de passe réel de l'utilisateur (souvent réutilisé ailleurs) qui dort sur l'appareil, non révocable à distance.
→ Stocker le JWT à la place : il expire, et `session_version` (BUG-068) permet déjà de le révoquer.

**4. Permissions Android à risque pour la revue Play Store.**
`app.json` déclare `SCHEDULE_EXACT_ALARM` et `USE_EXACT_ALARM` alors que rien dans le code ne planifie d'alarme exacte (les notifications utilisent des déclencheurs date/intervalle classiques). Google réserve `USE_EXACT_ALARM` aux réveils, minuteurs et calendriers ; une appli anti-gaspi qui la déclare s'expose à un rejet.
→ Retirer les deux lignes, reconstruire, vérifier que les rappels J-1 arrivent toujours.

### P1 — CI et outillage

**5. Suite backend : 58 minutes en CI, pour de mauvaises raisons.**
Avant le 09/09 la CI ne lançait que 7 fichiers de tests (BUG-070) et durait 2 min ; depuis que toute la suite tourne, 58 min. Cause vérifiée : aucun service MongoDB en CI (ni localement), le client Motor pointe sur `localhost:27017` et chaque appel attend le timeout de sélection (30 s) avant que le code n'avale l'erreur. Exemple : `test_billing_api_v1.py` remplace `users_col` par un faux mais pas `business_events_col` ; le handler appelle `track_business_event`, qui attend 30 s puis ignore l'erreur, et le test passe. Le même schéma se répète dans des dizaines de tests. S'ajoutent des variables CI jamais lues par le code (`MONGODB_URI`, `JWT_SECRET` ; le code lit `MONGO_URL`, `JWT_SECRET_KEY`) et une suite exécutée deux fois dans le même job (« fast gate » puis « complete »).
Mesure complémentaire : avec un timeout de sélection Mongo ramené à 0,5 s, la suite avance (44 % en 10 min, 0 échec, là où la suite normale restait bloquée plusieurs minutes sur un seul test), mais resterait autour de 20–25 min : l'absence de Mongo est le facteur principal, pas le seul. Un profil par test (`--durations`) complet reste à faire une fois un Mongo de test disponible.
→ Service `mongo` dans le job (ou client factice injecté partout), `serverSelectionTimeoutMS` court sous `APP_ENV=test`, un seul run, variables renommées, puis profilage des tests restants. Cible : moins de 5 min.

**6. Trois automatismes qui tournent dans le vide.**
- `auto-merge-pr.yml` attend un check nommé « Mobile E2E / Not required (changes filter) » ; le job s'appelle en réalité « …/ Not required or missing required APK ». Le portail ne s'ouvre donc jamais : tu merges à la main depuis des mois sans le savoir.
- Maestro nightly échoue chaque nuit ; `continue-on-error: true` sur la PR : l'E2E n'est plus une barrière, seulement du bruit.
- `codex-auto-fix.yml` se déclenche sur ces échecs.
→ Décision à prendre : réparer Maestro (ou le désactiver tant qu'il n'est pas réparé) et, pour l'auto-merge, soit corriger le nom du check, soit supprimer le workflow. Je recommande la suppression : tu veux garder la main sur le merge, et un auto-merge couplé à un auto-fix par IA fait atterrir du code sur `main` sans regard humain.

**7. La validation canonique ne démarre pas telle que documentée.**
`./scripts/ai-validate.sh` → « Permission denied » : les scripts sont en mode 644 dans git. Et côté backend, le script saute ruff, black et mypy parce qu'ils ne sont pas dans `requirements.txt` — alors que `.ai/core-rules.md` promet « mypy strict ».
→ `chmod +x` committé ; `requirements-dev.txt` avec ruff + mypy ; mypy non strict d'abord (115 erreurs à résorber), durcissement ensuite.

**8. Dépôt pollué.**
`frontend/.metro-cache/` : 7 330 fichiers, 12,8 Mo suivis par git malgré la ligne dans `.gitignore` (ajoutée après coup). `.project_assistant/memory.json` : 4,3 Mo, index d'un outil Windows avec ton chemin local en clair.
→ `git rm -r --cached` sur les deux.

### P2 — dette structurelle

**9. `backend/server.py` : 7 955 lignes, 91 routes.** Toute l'API dans un fichier ; 22 `except Exception:` dont 2 muets (`pass`/`continue`), 23 handlers sans type de retour.
→ Découpage en routers FastAPI par domaine (auth, stock, recipes, billing, admin, ocr, alerts, household), URLs inchangées, un domaine par PR.

**10. Frontend : nommage et typage.** `data/mockDashboardData.ts` (452 lignes) contient les types et helpers métier utilisés en production (`daysUntil`, `resolveStockItems`, `findExpiringSoon`) à côté de fixtures ; ~40 `catch (e: any)` ; `router.push('…' as any)`.
→ Extraire un `domain/stock.ts`, garder les fixtures sous `data/` ; `catch (e: unknown)` + helper `getErrorMessage` ; routes typées Expo Router.

Documentation en dérive.** 14 fichiers `.md` à la racine dont 9 figés depuis juin, 4 `DEBUG_*.md` dans `frontend/` ; `CLAUDE.md`, `.ai/test-policy.md` et le stack guide décrivent `frontend/__tests__/`, qui n'existe pas (les tests sont dans `utils/`, `integration/`, `smoke/`, `data/`) ; le README cite `backend_test.py`.
